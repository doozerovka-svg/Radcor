# Radcor-Prim: удобная покупка и руководства — план внедрения

> **For agentic workers:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Сделать B2B-каталог понятным с первого визита, помочь покупателю подобрать совместимый товар и оформить проверяемый заказ без звонка, а также дать ему короткие прикладные руководства в контексте покупки.

**Architecture:** Сайт остаётся лёгким HTML/CSS/vanilla-JS приложением с Express API. Каталог, карточка товара, корзина и оформление заказа работают с одним контрактом товара и упаковки; статические страницы «Руководства» используют тот же каталог для связанных товаров. Сервер является источником цен, доступности и суммы заказа — браузер не рассчитывает коммерчески значимые данные.

**Tech Stack:** HTML5, CSS3, vanilla JavaScript, Express 4, SQLite3 (с текущим JSON fallback), встроенный `node:test`, Playwright для браузерной проверки.

## Global Constraints

- Целевая аудитория: магазины запчастей, СТО, автопарки и дилеры в Молдове; основной язык RU, все новые пользовательские строки должны быть подготовлены к зеркальному переводу RO.
- Не показывать `0 MDL` как цену: если цена не доступна гостю, явно выводить «Цена после входа» и CTA на запрос условий.
- Не сохранять «оформленный» заказ только в `localStorage` и не обещать его обработку без фактической доставки на сервер.
- Сервер пересчитывает цену, упаковку, количество, доставку и итог; значения, присланные браузером, не являются источником истины.
- Текущие незакоммиченные файлы (`extract_urls.py`, `mol_catalog_scraped.json`, `product_links.json`, `scrape_mol.py`, `verify_snapshot.py`) не менять и не добавлять в коммиты этой работы.
- Дизайн сохраняет существующий бренд Radcor-Prim, но работает без горизонтальной прокрутки при ширине 320 px и соответствует WCAG 2.2 AA для новых и изменённых элементов.

## Что сейчас мешает пользователю

1. В каталоге нет карточки товара: покупатель не может проверить полный список допусков, документы, применимость, наличие и точную упаковку до добавления в заказ.
2. Переключатель объёма на клиенте линейно пересчитывает цену, хотя API принимает только SKU и на сервере всегда заменяет выбранную упаковку на `canister`. Итог в корзине может не совпасть с оформленным заказом.
3. Оформление заказа создаёт анонимную заявку с подставными контактами, не просит способ доставки, адрес, оплату или комментарий, а подтверждает результат системным `alert`.
4. Каталог загружает `products.json`, а админ/API — отдельную БД. Пользователь может видеть не те цены и доступность, которые использует сервер.
5. «Личный кабинет» и VIN-подбор частично демонстрационные: вход принимается с любым паролем, дашборд содержит статичные суммы, а API VIN всегда возвращает один автомобиль. Это подрывает доверие, если выглядит как рабочая функция.
6. На страницах без каталога `app.js` обращается к `#catalogGrid` без проверки. Это прерывает дальнейший JavaScript страницы, включая мобильную навигацию и формы.
7. В навигации и FAQ нет ответов в момент задачи: «какое масло выбрать», «как заказать», «что привезут», «как получить документы», «что делать с возвратом».

## Пользовательский путь, который должен получиться

```text
Главная / Каталог
  → поиск по артикулу, названию или допуску; либо «Подобрать по автомобилю»
  → карточка товара: применимость, упаковка, наличие, цена/условия, документы
  → корзина: количество, упаковка, срок и порог доставки видны до оформления
  → оформление: контакты → доставка → оплата → проверка → номер заявки
  → кабинет: статус, счёт/накладная, повторить заказ

Из любой точки
  → Руководства → короткая инструкция → связанные товары или помощь специалиста
```

## Критерии готовности

- Покупатель в три клика от поиска/подбора видит применимость товара, упаковку, статус наличия и понятный следующий шаг.
- В заказе, preview, базе и подтверждении совпадают SKU, `pack_id`, количество и серверная цена.
- Запрос не удаляется с экрана при сетевой ошибке; успешный запрос имеет номер и ожидаемый дальнейший процесс.
- Минимум шесть руководств доступны из меню, находятся поиском, содержат полезные шаги и ведут к релевантным товарам/поддержке.
- На мобильном устройстве 320 px каталог, карточка, корзина и checkout проходят без горизонтальной прокрутки и без недоступных элементов управления.
- Нет демонстрационных персональных данных, фиктивного VIN-результата или ложных обещаний о заказе в пользовательском интерфейсе.

## Проверка покрытия плана

- Ориентация: Task 1 и Task 3 создают навигацию по задачам, фильтры, поиск и карточки.
- Покупка: Task 2 и Task 4 обеспечивают корректную упаковку, цену, корзину, данные покупателя, доставку, оплату и подтверждение.
- Руководства: Task 5 определяет структуру, шесть первых материалов, связь с товарами и RU/RO-процесс.
- Повторная покупка: Task 6 заменяет статичный кабинет на реальные сведения после безопасной авторизации.
- Качество: Task 7 покрывает API, сквозной путь, доступность, метрики и безопасный rollout.

План не включает интеграцию с 1С/ERP, платёжным провайдером или коммерческим VIN-сервисом без отдельного выбора поставщика и доступа к их API. Интерфейсы для таких интеграций заложены в очереди C.
